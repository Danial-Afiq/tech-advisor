## Behaviour to implement

| Area | Planned behaviour |
| --- | --- |
| Recurrence | Scheduled instants are a configured UTC anchor plus multiples of exactly 14 days (336 hours). Manual runs and job duration do not move the anchor. |
| First run | Explicit deployment configuration defines the first scheduled instant; no surprise live scrape on every application startup. |
| Manual runs | An authenticated ADMIN can request all enabled sources or selected registered source IDs and provide a reason. Use the same runner, logging, and load controls as scheduled runs. |
| Concurrency | Only one pipeline run is active globally. A competing manual request receives `409` with the active run ID. A due scheduled slot remains pending until the active run finishes. |
| Retries | Deduplicate retried admin submissions using an idempotency key tied to the authenticated actor and request; a reused key with different parameters is rejected. |
| Downtime | On recovery, coalesce overdue slots into one catch-up run and record how many were missed. Resume the original cadence; do not issue a burst of historical scrapes. |
| Failures | Isolate source failures so remaining sources can run. Report `SUCCESS`, `PARTIAL_FAILURE`, `FAILED`, or `INTERRUPTED`; keep progress and error metadata. |
| Load | Sequential sources initially, bounded pages/items and HTTP timeouts, per-source pacing and cooldowns, bounded retry/backoff, and support for Retry-After. Manual triggers retain these limits. |

“Precisely once” means one durable admission per scheduled slot, with no duplicate dispatch during healthy operation. Neither exact wall-clock execution during downtime nor exactly-once external effects after a crash can be guaranteed. Persist scheduled and actual start times and lateness. Use source item identity/upserts at the persistence boundary to make recovery safe.

Avoid day-of-month cron steps and a bare startup-relative `@Scheduled(fixedDelay = 14 days)`: neither expresses the durable anchored behaviour above.

## Architecture and persistence

Use Spring `TaskScheduler` to arm the next persisted due instant and a bounded `TaskExecutor` to run ingestion. On startup, reconcile persisted state before arming the scheduler. Both scheduler and controller call `IngestionOrchestrator`; adapters never own scheduling or HTTP request lifecycle.

Prefer a small PostgreSQL-backed coordinator over adding a broker or a full workflow platform. Preserve the canonical 13-table Sprint 1 foundation by storing one reserved `INGESTION_COORDINATOR` row in the existing `system_log` table, with durable anchor/next-due/active-run state in JSONB. Serialize admission using a short row-locking transaction; add a unique partial index to enforce one coordinator. Ordinary run rows use component `INGESTION_RUN`. Document the reserved row so operational history queries exclude it.

Admission atomically persists the run record and coordinator claim before dispatch. A small recovery sweep handles accepted-but-not-dispatched work and interrupted runs. Do not hold a database transaction open during network ingestion. Use an owner token, heartbeat and expiry for active claims; reject stale-owner progress/finalization writes. The worker must stop if ownership is lost. Recovery marks abandoned work interrupted rather than blindly replaying partially completed external work. Validate these rules with real PostgreSQL concurrency tests before enabling scheduling.

Create the next available Flyway migration (currently V2) for `system_log`: `id`, `component`, `status`, `message`, `metadata JSONB`, and `created_at TIMESTAMPTZ`, plus relevant indexes. Recheck migration numbering before implementation/merge. Log writes must commit independently of failed ingestion work. If initial persistence is unavailable, fail closed without contacting sources.

Run metadata includes `runId`, `triggerType`, authenticated `requestedBy`, optional `reason`, `scheduledFor`, `requestedAt`, `startedAt`, `finishedAt`, `durationMs`, selected sources, `processedPayloadCount`, `errorCount`, `errorStackCount`, per-source results, skipped/cooldown counts, and bounded sanitized error details. Capture progress so a crash does not erase all counters. Count a processed payload only after the configured ingestion sink accepts it; track rejected and duplicate payloads separately. `errorStackCount` counts captured exception stacks, not stack frames; `errorCount` also includes validation failures without exceptions.

## Source extension contract

Suggested package: `com.springboot.backend.ingestion`, with `api`, `core`, `source`, `persistence`, and `config` subpackages.

Define `IngestionSource` with a stable `sourceId()` and an ingestion method accepting a `SourceContext` and a bounded payload consumer. Context supplies the run ID, clock, cancellation/ownership check, and source policy. The consumer validates and hands normalized payloads to an `IngestionSink`, recording success only after acceptance. Central orchestration handles lifecycle and summary logs.

Define a normalized payload envelope with source ID, external item ID, observation timestamp, payload type, and source data. Keep domain mapping behind the sink; do not create speculative catalogue/recommendation tables for this ticket. The simulated source and test sink exercise this same contract and must identify their output as simulation, not real market data.

Register adapters as Spring beans, validate unique IDs at startup, and use an enabled-source allowlist. Admin requests choose registered IDs, never arbitrary URLs or code. Include deterministic success and failure fixtures enabled only in demo/test profiles.

The source integration guide will show a complete example adapter, registration/configuration, payload identity, sink handoff, timeouts/rate limits, exception handling, fixture tests, and a checklist for API credentials and permitted source access. New adapters should require no controller or scheduler edits.

## Admin API and UI

| Endpoint | Purpose |
| --- | --- |
| `POST /api/admin/ingestion/runs` | Validate source IDs/reason and idempotency key; admit work asynchronously; return `202` with run ID and status URL. |
| `GET /api/admin/ingestion/runs/{runId}` | Return lifecycle state, progress, counters, and per-source result summary. |
| `GET /api/admin/ingestion/runs` | Paginated history with trigger/status filtering. |
| `GET /api/admin/ingestion/sources` | Available sources and enabled/cooldown state. |
| `GET /api/admin/ingestion/schedule` | Next scheduled instant, interval, and current run. |

Return `400` for invalid input, `401` for unauthenticated callers, `403` for non-admins, and `503` if admission cannot be persisted. Derive actor identity from server authentication; never trust a submitted role or user ID. API history must not expose credentials, response bodies, or raw sensitive stack traces.

Authentication is an implementation dependency: integrate the team's Spring Security work before making these routes available. If it is not ready, keep production endpoints disabled/denied and use test-profile authentication for the demo; a mock admin is not sufficient for production acceptance. Document OpenAPI contracts alongside implementation, selecting a compatible dependency then.

Add a small admin ingestion panel to React once the authentication contract is available: source selection, optional release reason, Run now, progress/result, last runs, and next scheduled run. Disable submission while active and handle server-side conflicts. Include the manual-demo command in documentation so the backend flow is independently reproducible.

## Verification and acceptance evidence

- Fake-clock tests: no run before due; one admission at due; next slot exactly +336 hours across month/year boundaries; manual execution leaves schedule unchanged; completion time does not cause drift.
- PostgreSQL integration tests: migration, durable log retrieval after restart, concurrent scheduler instances, manual/scheduled races, idempotent manual retries, dispatch failure, crash recovery, stale ownership and database failure before admission.
- Source tests: invalid payloads, success counts, duplicate handling, bounded exception logs, partial failure with later sources continuing, cooldown and retry limits, cancellation and request timeout.
- API security tests: anonymous and USER access denied; ADMIN accepted; invalid/disabled source rejected; history protected; server-derived actor recorded.
- Demo: start local PostgreSQL and backend with demo fixtures; submit an admin run; poll to completion; query `system_log`; show persisted timestamps, processed count and exception-stack count. Repeat with a failing fixture. Restart and retrieve the same history.
- Demonstrate the scheduling path with an injected clock/test configuration rather than waiting 14 days. Verify the production interval remains 14 days.
- UI verification: admin starts a run, sees progress and result, and sees an unchanged next scheduled date; non-admin cannot use the panel or API.
